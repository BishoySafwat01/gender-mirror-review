Gender Mirror

A review of the proposed cross-gender rule editing workflow against the current automation implementation. The simulation is a reasonable next step. Production rule writes require a separate approval gate and a narrower, tested write path.

Decision

Approve the review workflow as a controlled experiment. Do not treat the apply flag as a routine configuration change.

Proceed

What exists today

The implementation baseline matters because several promises in the plan depend on behavior already present in the editor.

Observed in the repository
  • A read-only Gender Mirror page displays existing initial rules side by side as simulated chats.
  • The normal rule update endpoint uses a row lock and an If-Match revision check.
  • Editing later reply steps can synchronize those fields to same-store rules in other countries.
  • Updating an active rule can schedule rechecks of recent unanswered messages.
  • Creating an initial rule can populate missing country variants.
  • Keyword changes have their own staged publication cycle.
Specified in the plan, not found in this checkout
  • Proposal table, generation worker, and model-backed checks.
  • Backend endpoints for proposal review, approval, regeneration, and undo.
  • A server-side GENDER_MIRROR_APPLY_ENABLED setting.
  • Integration tests for approval, undo, and scope isolation.

The existing page is useful groundwork; it should not be presented as evidence that proposal review or apply mode already works.

Findings

P0 blocks production application; P1 requires a design decision before implementation; P2 requires validation or documentation. Severity reflects the impact if the plan uses the current create and update paths. Expand a finding for the mechanism, required action, and source.

P0Updating one country can modify sibling countries
Mechanism and impact

The current update endpoint synchronizes changes to second and third replies across other countries for the same store. An approval routed through that endpoint can exceed the plan's “same country” boundary.

Required action

Use a scoped apply operation that updates only the intended target rule, or make the wider write set explicit and reviewable. Test that every other country remains unchanged.

Evidence: automations.py:1106–1133 · initial_rule_copy.py:139–174 · plan §§2.4, 3.5.

P0Creating a missing target can fan out to other countries
Mechanism and impact

The plan allows approval to create a missing target rule in the off state. The current create endpoint calls missing_country_copies, which creates other missing country variants for a single-country initial rule when its scope qualifies. “Off” limits activation, but the extra records still violate the promised write scope.

Required action

Give mirror-driven creation an explicit no-fan-out path. Assert that the only new rule is the reviewed target.

Evidence: automations.py:620–625 · initial_rule_copy.py:59–110 · plan §3.4.

P0Rule updates may trigger message rechecks
Mechanism and impact

When an active rule's text or keywords change, the normal update path may schedule a recheck of recent unanswered messages. The plan says no conversations are read or changed and no messages are sent. That assurance cannot be made from the proposed reuse of the editor path alone.

Required action

Define whether approval is allowed to re-evaluate existing conversations. If it is not, suppress the recheck and verify that approval and undo schedule no outbound work.

Evidence: automations.py:1149–1169 · plan §§3.4–3.5.

P0Stale approval and undo are underspecified
Mechanism and impact

The proposal schema records a source revision and a target snapshot, but the plan does not require comparison with the current target revision at approval or undo. A later manual edit, scope change, or second approval could be overwritten.

Required action

Lock the proposal and both rules in one transaction. Revalidate workspace, brand, country, opposite merge, and source and target revisions. Return a conflict for stale proposals. Undo only if the target still matches the revision produced by that approval.

Evidence: automation.py:112–117 · revision_guard.py:5–14 · automations.py:995–1013 · plan §6.1.

P1The transformation rule changes meaning between sections
Mechanism and impact

The stated goal is to change only words addressing the customer. An example changes “I am going” from masculine to feminine, which changes the speaker's gender. A model can follow either interpretation and still pass shape and number checks.

Required action

Define whether the store voice has a gender and whether first-person statements may change. Add paired counterexamples from the dialects in use before model evaluation.

Evidence: plan §§1.3–1.4 and 4.2.

P1The number-line rule conflicts with complete gender conversion
Mechanism and impact

The plan copies any line containing a digit byte for byte. A line such as “Take 2 for 160” can include a gendered imperative. Copying it protects the price but leaves the customer address unchanged.

Required action

Either protect numeric spans while allowing the surrounding address to change, or flag mixed lines for manual review. Never label an unchanged gendered number line as fully converted.

Evidence: plan §§1.3 and 4.4.

P1The proposed model contract covers fewer fields than the feature
Mechanism and impact

The draft prompt returns three step arrays. The feature also includes per-page variants, two private follow-ups, and keywords. The current frontend data type reflects those additional fields. Mapping a source page variant to the target store's page IDs is not specified.

Required action

Define a field-by-field proposal schema and deterministic page mapping. Run the same checks on every writable text field after generation and after each manual edit. Treat keywords separately from model output.

Evidence: genderMirrorApi.ts:28–39 · plan §§3.3 and 4.2.

P1Keyword copying has delayed publication semantics
Mechanism and impact

Keyword changes are staged while the previous index remains live, then published after the index is built. “Approved” and “effective” may occur at different times. Step-specific keywords live in step_settings as well as the top-level rule.

Required action

Specify which keyword sets are copied, whether approval waits for index publication, and what status appears if indexing fails or remains pending.

Evidence: automation_keyword_index.py:1–55 · automation.py:145–146 · plan §3.3.

P1Proposal delivery after save needs a recovery path
Mechanism and impact

The plan calls for a best-effort enqueue after a successful rule save that “never raises.” That protects editor latency, but a queue or database failure can silently leave a saved source rule without a proposal.

Required action

Persist a durable job or event with the save, or add reconciliation that detects eligible saves without a proposal. Make retries idempotent by source revision and target scope.

Evidence: plan §§3.1 and 6.1. This is a design risk in the proposed flow; the hook is not present in the checked-out backend.

P2The simulated chat is a text preview, not a behavior test
Mechanism and impact

The current chat pane inserts a fixed “What is the price?” customer message for the second and third steps. It does not execute matching, timing, per-page selection, or delivery behavior.

Required action

Label the view as a preview and show the exact field-level diff beside it. Keep behavioral testing in automated integration tests rather than implying the mock conversation validates delivery.

Evidence: ChatPane.tsx:25–48 · plan §5.3.

P2The stated example count and success criteria are unverified
Mechanism and impact

The plan promises about 40 pairs and a separate example artifact, but supplies no eligible-rule inventory or quality target. The existing comparison view selects a single active or newest rule for a brand/country slot, potentially hiding duplicate rules.

Required action

Count eligible rules and duplicates from production data before committing to a sample size. Track acceptance without edits, review time, model failures, and protected-token violations.

Evidence: genderMirrorExisting.ts:151–164 · plan §6.3. Production data was not inspected.

P2The plan should be updated before it becomes the delivery baseline
Mechanism and impact

The existing phase-one page is described as new work. The PDF lists an out-of-scope and risks section that is absent from the supplied pages, and its last numbered point is cut off.

Required action

Publish a revised plan separating current behavior, new work, open decisions, and acceptance tests. Attach the risk section and full assumptions list.

Evidence: GenderMirrorPage.tsx:11–15 · plan contents page and final page.

Recommended release sequence

Each step produces evidence for the next decision.

1. Establish the baseline

Inventory eligible source and target rules, hidden countries, duplicate slots, and missing targets. Select a representative sample across brands, genders, countries, and text structures.

2. Release simulation

Persist proposals and checks, show exact diffs and a clearly labeled chat preview, support edit/reject/regenerate, and record simulation approval without modifying rules.

3. Measure review quality

Compare acceptance rate and review time with manual editing. Record every protected-token failure and every case in which the reviewer changes the model output.

4. Decide on apply mode

Only after the acceptance criteria pass, implement and test a scoped write operation, then enable it as a separate release decision.

Decision rule

Keep the feature in simulation if the proposal is correct but the write path is not isolated, or if reviewers spend as much time correcting proposals as they would editing the target directly. Enable apply only when both product value and data integrity are demonstrated.

Strongest dissent: a small sample may not justify building the complete generation worker and review workflow. A narrow pilot inside the existing page reconciles that concern with the need to test real operator usage.

Decision memo

A concise note suitable for the implementation discussion.

I support shipping the Gender Mirror review workflow in simulation mode. It should generate proposals from a representative set of existing rules, show exact field-level changes, run server-side checks, and record reviewer decisions without writing production rules. I would hold apply mode until the write path is isolated and tested. The current rule update path can synchronize later replies to other countries and recheck recent unanswered messages; the create path can generate missing country copies. Those behaviors exceed the proposed same-country, no-conversation-impact scope. Approval and undo also need revision and scope checks against the live source and target rules. Before we commit to apply mode, please define the transformation contract for customer versus speaker gender, mixed number/gender lines, per-page variants, follow-ups, and keywords. Then measure edit-free acceptance and review time on real examples. Treat enabling the apply flag as a separate release decision backed by integration tests and those review results.
